## 清单(按信号走向)

### 第 0 段|时钟地基
- **0.1** EC2 chrony 偏移+漂移(vs NTP 池 / AWS Time Sync)。目标:钟差已知且 <1ms,
  否则单向延迟全部作废。
- **0.2** 三外源时间戳可比性:Kalshi 消息 ts / cfbenchmarks `received_at` /
  Coinbase ts,各自与本机钟的系统性偏移估计。

### 第 1 段|行情入站(事件 → 我们看见,recv_mono_ns 口径)
- **1.1** Kalshi WS orderbook_delta:交易所 ts → recv。
- **1.2** Kalshi WS cfbenchmarks_value:source_ts → received_at → recv。
  撤退警报器官方通道,其延迟直接加进撤退全链。
- **1.3** Coinbase WS:事件 ts → recv;与 1.2 差值 = 民间警报器领先量。
- **1.4** 进程内热路径:帧到达 → 解析 → 策略可见(bench 复测)。

### 第 2 段|决策
- **2.1** 策略计算延迟(bench_engine 复测,预期 µs 级,非瓶颈)。
- **2.2** 签名 p99 ~450µs(已测,引用 LATENCY_FACTS,不重测除非环境变更)。

### 第 3 段|出站 ★全链最大未知★
- **3.1** 网络基线:EC2 us-east-2 → api.elections.kalshi.com TCP/TLS RTT;
  冷连接 vs keep-alive 热连接分开;解析目标区域记录在案。零风险,先跑。
- **3.2** 下单 ack 延迟(demo):REST POST → ack;若存在 WS/FIX 下单通道一并测。
- **3.3** 撤单 ack 延迟(demo):**全清单最重要单项**,状态撤退的物理下限。
- **3.4** 批量撤:1/5/10/20 单的耗时曲线(batch endpoint 与逐张对比)。
- **3.5** 自家限流器排队延迟:Token Rule 参数下,突发第 N 个请求的等待分布。
- **3.6** 结构上限核算:官方限速 × 铺开价位数 → 全撤理论最短耗时。
  先算(费率/限速文档 + Token Rule)后测。此数约束 E4 铺开宽度,可能一票否决。

### 第 4 段|确认回路
- **4.1** fill 推送延迟:撮合 → WS fill 消息 recv(库存感知延迟)。
- **4.2** 自单可见延迟:ack → 自单出现在行情流(闭环自检,兼校验 1.1)。

### 第 5 段|复合链(对表 E4)
- **5.1** 撤退全链:警报事件 recv → 最后一张挂单撤销 ack。
  = 1.2/1.3 + 2.1 + 2.2 + 3.5 + 3.4。空载与风暴负载(并发撤 N 单)两种条件。
  **此数对入 E4 速度→盈亏曲线,落点即我们的档位。**
- **5.2** 站位全链:决定挂 → 挂单在行情可见(秒级需求,验证即可)。
