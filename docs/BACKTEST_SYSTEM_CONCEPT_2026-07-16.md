# 回测系统构思 — 1:1 验证平台(操作员共同设计,2026-07-16)

**Status: CONCEPT — 遵从 docs/PLAN_MM_TEST_PROGRAM.md(总测试门 G1~G9)
的框架;本文只定架构哲学与缺件清单,不新设门、不改门序。**

## 一、什么叫 1:1(架构的第一原则)

**同一个策略引擎,三种插座。**策略代码只写一份(C++ 引擎),插到:
- **回放插座**(backtest):喂历史消息流,交易所由模拟器扮演;
- **影子插座**(shadow):喂实时消息流,下单动作只记录不发出;
- **实盘插座**(live):同一引擎,真发单(G7+ 之后,操作员逐门授权)。

为什么这是第一原则:市面上回测失真的头号原因是"回测代码 ≠ 实盘代码"
——重写一遍必有偏差。同一引擎换插座,G6(影子一致性门)才可能过:
同一天数据,回放跑一遍、影子跑一遍,决策序列必须逐条一致。

## 二、1:1 的生死点:成交模拟器(W-FS1,总测试计划已挂号)

回放行情容易,难的是回答"我挂的单成交了吗"。历史数据里没有你,
你的单子会改变队列——这是回测的原罪,只能用**区间**回答:

- **悲观口径(go/no-go 依据,GUARDRAILS 钉死):**只有价格**穿透**你的
  价位才算成交(排队最后、部分成交按最坏、撤单在途期间算暴露);
- **乐观口径(仅诊断):**触价即成交;
- 真实落在两者之间,**所有晋级决策只看悲观口径**。乐观-悲观差距大的
  策略 = 对成交假设敏感 = 危险,单独标记。

模拟器必备件:排队位置模型(L2 深度做上界)、部分成交、撤单在途延迟、
自成交防护、**费用逐笔精确**(7%×p×(1-p),费率事实需先 ratify)、
结算持仓(合约到期按赛果清算,库存不是平出来的是判出来的)、
E4 定点运算。

## 四、账房合同(产物纪律,沿用总测试计划 §3)

每次回测运行 = 一份收据包:输入数据指纹、引擎 commit、配置指纹、
延迟参数来源、悲观/乐观两套 NetPnL(逐日分块)、费用总额、
最大库存与回撤、gap 不报价时长。**无收据的回测结果不存在。**
同参数重跑必须逐字节复现(确定性:种子、消息顺序、定点运算)。

## 五、建造顺序(缺件清单,按依赖排)

1. **费率 ratify**(小,先行):费用公式与实测对账,写入 facts。
2. **W-LAT-BENCH-01**:延迟参数实测(已批,Tier 1-3)。
3. **W-B9-BATCH-01**:批量读取引擎(已规划待批)。
4. **W-FS1 成交模拟器**:本构思的主工程,依赖 1-3 的数字;
   规格评审时做"事前验尸"(怎么死:队列假设过乐观/费用漏算/
   结算路径没模拟)。
5. **同引擎回放插座接线**:策略引擎喂档案消息流,G6 预演。
6. 以上全绿 → deep03 候选进 G3/G4,按总测试门走。
