Auditor: fresh-context agent, no part in implementation; offline probes only
(no live Kalshi calls, KALSHI_ALLOW_LIVE never set). Scope: the panic
kill-switch CLI (apps/panic.cpp) vs PLAN_RISK_KILLSWITCH §1/§3 + the operator

This was the hardest audit of the project so far — the single execute gate
took THREE reject/fix rounds, each closing one more URL-authority bypass
class. Final verdict ACCEPT. The core lesson is preserved in BACKLOG: a kill
switch that re-derives its own connect-target host must parse the FULL
RFC-3986 authority (terminate at `/?#`, strip userinfo at last `@`, strip
port, `[::1]`, case-fold) — anything less is defeatable under
KALSHI_HOST_UNSAFE_OVERRIDE.

## Round 2 — VERDICT: REJECT
The round-1 loopback guard used substring `find("://localhost")` /
`find("://127.0.0.1")` — defeatable by `localhost.evil.com`,
`127.0.0.1.evil.com` (suffix) and `127.0.0.1@evil.com`,
`127.0.0.1:18099@evil.com` (userinfo — curl dials the host after `@`). N1-N4
confirmed correctly applied. Fix: replaced with exact, userinfo-aware host
equality (authority to first `/`, strip userinfo at last `@`, strip port,
`[::1]`); regression test covers all five vectors; env.cpp parse_url's shared
userinfo quirk filed to BACKLOG.

## Round 3 — VERDICT: REJECT
The round-2 guard terminated the authority at `/` only, never `?`/`#`. So
`https://external-api.kalshi.com?@127.0.0.1` → authority
`external-api.kalshi.com?@127.0.0.1` → rfind('@') → host `127.0.0.1` →
loopback=1 → unarmed drill, while libcurl ends the authority at `?` and dials
external-api.kalshi.com (confirmed: `curl -v "https://target.invalid?@127.0.0.1"`
→ "Could not resolve host: target.invalid"). Fragment form
`realhost#@localhost` identical. Fix: terminate the authority at the first of
`/?#` before any userinfo/port stripping + case-fold the host; regression
test adds the `?@` / `#@` / `?x=@` vectors.

## Round 3 re-verify — VERDICT: ACCEPT (VERBATIM)

Verified against the current `base_host_is_loopback` (rebuilt, exact-copy probe over 18 authority-grammar corners + libcurl connect-target confirmation on the two that mattered, all offline via loopback / RFC-2606 `.invalid` targets — no live calls):

Every form where the guard returns `loopback=1` either dials a genuine loopback host or is rejected by libcurl before any transmit. Every form where libcurl would dial a non-loopback host, the guard returns `0` (refused). No remaining divergence is live-fire exploitable:
- `?@` / `#@` / `?x=@` authority-terminator vectors → now `0` (fixed). ✓
- percent-encoded `%40`, control chars (tab/newline/space), empty host, trailing dot, unicode lookalike, `[::1]@evil.com` → all `0`. ✓
- `https://nothere.invalid\@127.0.0.1` → `loopback=1`, but curl also dials **127.0.0.1** (backslash is normal userinfo to curl; both agree — real loopback, safe). ✓
- `https://[::1]nothere.invalid` → `loopback=1`, but curl **rejects the URL** ("Port number was not a decimal number") — no connection, no transmit. ✓
- `HTTPS://127.0.0.1` (uppercase scheme) → dials 127.0.0.1, loopback, safe. ✓
