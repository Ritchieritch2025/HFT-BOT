# W-K1 AUDIT VERDICT: ❌ REJECT (remediable — two blocking defects, each a ~3-line fix; everything else sound)

一行白话:这个"查账工具"整体做得很扎实(签名、只读、精度、现场验收都是真的),但它的核心承诺——"证明不了零挂单就必须报警(exit 1)"——被我用实验打穿了一个洞:翻页翻到上限被截断时它仍报"清零、放行";另外它的钱数解析器会把非 ASCII 数字悄悄算成错的钱数。这两处都违反宪法 S2/D3/D5,按 GUARDRAILS "violating any of these is an automatic reject" 只能退回修复;修复很小。

## BLOCKING

**B1 — Pagination truncation in `--assert-zero-resting` is FAIL-OPEN (S2 violation; falsifies the commit's own claim "UNPROVABLE ⇒ exit 1").**
- Code: `tools/account_view.py` `_paged()` — at `pages >= MAX_PAGES` it prints a stderr WARN and `return`s normally; `main()` counts no drop for it, so an *incomplete* enumeration yields the same rc=0 "clear" verdict as a complete one.
- Proof (I ran it against a local mock that loops `{"orders": [], "cursor": "AGAIN"}`): WARN printed, then `resting orders: 0 (ZERO — clear)`, EXIT CODE 0 with a truncated enumeration.
- Why it matters: this flag is THE panic-verify primitive W-K2 will build on, and its consumers read rc, not stderr. The same function already treats a *different* server-contract violation (a leaked executed order) as UNPROVABLE ⇒ rc 1 — the standard is applied inconsistently within one function. D2's own text calls silent truncation "the most dangerous failure class we have"; here the WARN exists but the machine verdict lies.
- Fix shape: in `_paged`, raise `AccountViewError` (or count truncation into `all_drops`) at MAX_PAGES. Add the missing test.

**B2 — `parse_e6` accepts Unicode digits and computes GARBAGE money values; its claim to share `gold_load.parse_e4`'s rejection rules is false (D3/D5).**
- Root cause: `_DEC_RE` uses Unicode-aware `\d`; `tools/gold_load.py:45` deliberately uses `[0-9]`. The digit-accumulation `ord(c) - 48` then mis-values non-ASCII digits instead of rejecting them.
- Proof (executed): `parse_e6('4.72696٠') -> 4728544` (wrong value, accepted); `parse_e6('١٢٣') -> 175947000000` (garbage); `gold_load.parse_e4('٥.٠٠') -> REJECT`.
- Realistic exploitability is low (input arrives from Kalshi over TLS), but this is the money boundary for panic/reconcile; the fix is one character class. All other adversarial inputs behaved correctly ("1.", ".5", "+1.5", "1e3", "1.2345678" rejected; "007"→7e6, "-0"→0 match parse_e4; huge ints fine; int/float inputs rejected).

## NON-BLOCKING

**N1 — urllib follows redirects and forwards KALSHI-ACCESS-KEY/-SIGNATURE headers to the redirect target (probe-proven), including cross-host.** Method stays GET, signature is path+timestamp-bound so replay value is small, but a redirect-controlling middlebox harvests the key id + one valid signature. Recommend refusing redirects (fail closed on 3xx).

**N2 — "cents = floor of balance_dollars, VERIFIED-LIVE" over-claims from one sample.** 23.2614→2326 is consistent with floor AND round; if the exchange actually rounds, a balance like 23.2699 will spuriously fail `get_balance` closed. Direction is safe (fail-closed) but the RESULT should say "consistent with floor (one sample); round not excluded". A mutation `cents == round(...)` passes the current suite — add a discriminating fixture with the fix.

**N3 — Honesty-of-record gaps, must land in the exit ritual:** the commit message says the src/storage.cpp incident is "noted in SESSION_LOG", but no W-K1 SESSION_LOG entry exists at audit time; the RESULT header cites "audit report in docs/plan_audits/" which didn't exist before this audit. The storage.cpp story itself checks out: `git status` clean, file untouched by 342b798, no stray modification at HEAD.

**N4 — Subaccount asymmetry unrecorded (matters for W-K5, not for zero-resting):** GET /portfolio/orders `SubaccountQuery` "If omitted, defaults to all subaccounts" (openapi.yaml:3885) — the panic primitive correctly sees ALL subaccounts' resting orders. But GET /portfolio/positions uses `SubaccountQueryDefaultPrimary` "Defaults to 0" (openapi.yaml:3892) — `get_positions` silently returns PRIMARY-ONLY. Harmless today; the W-K5 reconcile built on this view would under-count positions if subaccounts ever exist.

**N5 — Count gate is looser than spec, losslessly:** `_e4` accepts 3–4dp counts though FixedPointCount responses "always emit 2 decimals". No precision loss; footnote only.

**N6 — Fields ignored that downstream consumers may want** (all optional in spec): `order_group_id`, `subaccount_number`, `expiration_time`, `no_price_dollars` (orders); `balance_breakdown`/IndexedBalance (balance); `total_traded_dollars`, `last_updated_ts`, `total_cost_shares_fp` (positions).
