# DeepResearch V3 统一实验 Registry

## 它解决什么问题

这个 Registry 把 DeepResearch V3 的 106 个原子研究方向放进同一套“从假设到现金 PnL”的语言里。它首先追求覆盖面，再用统一门槛淘汰不能落地的想法。

**106 项不等于 106 个策略。** 市场现象、相关性、模型组件、数据目录和控制实验都可以进入 Registry，但只有同时具备可实时观测的信号、确定动作、执行场所、可执行基准和扣除成本后的逐路径 PnL 定义，才有资格称为策略。未知 PnL 不能记作 0，理论中间价收益也不能冒充现金收益。

## 每个实验必须回答的十个问题

| 字段 | 必须说清楚的内容 |
|---|---|
| 假设 | 经济机制是什么，什么结果会证伪它 |
| 信号 | 实盘时观测什么、用哪一个时钟、何时触发、方向如何解释 |
| 动作 | 触发后买卖哪一边、报什么价格和数量、何时撤单或退出、何时停止 |
| 执行场所 | 例如 Kalshi CLOB、Kalshi RFQ 或多市场路由；不能只写“交易” |
| 基准策略 | 同一机会集上与“不交易”、固定报价或其他可执行政策比较 |
| PnL | 按订单/成交路径计算相对基准的增量现金 PnL，并说明未成交与零触发 |
| 成本 | 手续费、点差、滑点/冲击、下单与撤单延迟、库存/结算/作废风险、抵押与资本占用 |
| 现有数据 | 当前数据能直接计算哪些信号、成交代理、markout、覆盖率或结算结果 |
| 数据缺口 | 缺少什么会阻断信号、执行或 PnL，不能用默认值掩盖 |
| 补数途径/API | 可从内部采集、交易所私有事件或外部 API 补什么，以及时钟、授权、许可和历史覆盖是否已验证 |

没有具体动作和 PnL 定义的条目仍可保留以铺研究广度，但不会被标成策略。

当前 V1 快照中，106 项里有 80 项是“动作型实验设计”，26 项是无动作的研究问题、信号、模型组件或控制；现阶段 `strategy_eligible_now=0`。这不是把收益记成 0，而是明确表示费用、成交、时钟、结算、私有状态、child 策略或外部数据等硬门尚未闭合。

## `computed_class` 的四种结果

`computed_class` 由字段完整性和阻断项计算，不由作者主观填写：

- `RESEARCH_QUESTION`：只有待证伪的问题或机制，尚无可复现的实时信号。
- `SIGNAL`：已有可复现信号，但动作、场所、基准或费用后 PnL 合约不完整。
- `EXECUTABLE_STRATEGY`：假设、信号、确定动作、场所、可执行基准和逐路径费用后 PnL 全部完整，且没有关键阻断项。
- `BLOCKED`：目标方向明确，但关键数据、时钟、权限、成交模型、费用、结算、风险门或执行基础设施缺失。Registry 同时记录它原本被阻断在哪一级。

`BLOCKED` 不表示假设失败，也不表示收益为零；它只表示当前证据不足以安全地进入下一阶段。

## 外部体育数据的硬规则

需要比分、局/盘状态、阵容、伤病、开赛状态、外部赔率或赛事格式的实验，必须在顶层直接标记外部体育数据依赖及其可用状态。

- 当前未采集或未验证时，标记 `MISSING`、`CLOCK_BLOCKED`、`LICENSE_BLOCKED` 等明确状态。
- 缺失策略固定为 `BLOCK_NO_IMPUTE`：不从盘口价格、市场标题、时间段或其他代理变量反推真实体育状态。
- 若原实验本来只研究明确命名的内部代理（例如 scheduled-start proxy），真实比赛状态只能登记为 `OPTIONAL_REFINEMENT`；核心实验可以保留，但必须继续叫“代理”，不能改名成真实 in-play 状态。
- 外部 API 只记作候选补数途径；在接口权限、字段语义、事件映射、源时间戳、历史可得性和使用许可逐项验证前，不视为已有数据。
- 外部数据补齐后仍需点时可得性测试，防止用事后修订的比分、阵容或赔率污染回测。

因此，缺外部体育数据的条目可以保留假设和未来动作设计，但不能被硬推成可执行策略。

## RFQ 的特殊边界

公开 RFQ create/delete 数据是 **unsigned**。它可以支持到达率、规模、生命周期和 CLOB 影响等统计，但不能可靠推出请求者想买还是想卖。

组合 RFQ 的 leg side 描述合约组成，也不等于真实交易方向。直接 RFQ 报价动作和现金 PnL 必须绑定私有的 accepted side、quote/confirmation、实际 fill、费用及结算记录；这些信息缺失时，相关条目只能是 `SIGNAL` 或 `BLOCKED`，不能宣称 RFQ 做市策略已成立。

MVE 不复用 RFQ 数据契约。MVE 直接交易必须单独绑定 exact-version MVE catalog、leg/orientation/payout matrix、私有 package order/ack/fill/fee、同步 hedge-leg L2、仓位和结算。公开 RFQ release 缺失不会阻断 MVE，反过来也不能拿 RFQ 事件冒充 MVE package 执行。

## 商业 PnL 的成本边界

单笔策略 PnL 至少扣除交易费、点差、滑点/冲击、下单/撤单/退出延迟、库存与异常结算损失、抵押和资本成本。`P10-COMMERCIAL-ROC-COST` 再强制加入数据源/许可/API、云计算/存储/请求/出网、运营人工/值班、事故损失和修复成本，并使用封闭 UTC 会计周期和冻结的共享成本分摊规则。任何成本未知都保持 `BLOCKED`，不会默认为 0。

## 生成与校验

在仓库根目录运行：

```bash
python3 tools/experiment_registry.py --write
python3 tools/experiment_registry.py --check
```

- `--write` 根据代码中的规范定义刷新 `EXPERIMENT_REGISTRY_V1.json`。
- `--check` 离线校验 106 个唯一 ID、字段完整性、分类逻辑、阻断项和内容哈希，并检查已提交 JSON 是否与生成结果一致。
- 校验器不只验 SHA。即使有人篡改字段后重算 card/registry SHA，`LIVE` 权限、空动作/基准/PnL、未知成本状态、外部数据插值、RFQ 方向注入、坏 L2 日期、缺失证据绑定或伪造 summary 也会被语义门拒绝。
- 106-ID 权威清单保存在 `sources/DEEP03_ATOMIC_DIRECTION_AUTHORITY_V1.json`；校验器同时核对该独立清单、来源计划 SHA 和所有本地结果证据文件 SHA。

这两个命令只读写本地 Registry 文件；它们不访问网络、AWS 或交易所，也不下单。

## 从广度 Registry 到实盘的升级门

条目不会因为出现在 Registry 里自动升级。每一级都要留下可复核收据：

1. **Breadth Registry**：登记所有可证伪方向，明确当前类别、所需数据和失败条件；不得输出盈利结论。
2. **Signal test**：使用预先登记的干净日期和严格时间语义做样本内/样本外检验；报告全部机会、零触发与失败结果，并控制多重检验和数据泄漏。
3. **Shadow**：在不下单的条件下按确定规则生成订单意图；用严格成交模型、真实费用、延迟、结算、容量和可执行基准计算路径级 PnL，并完成风险停止条件。
4. **Micro-live**：取得独立、明确的一次性执行授权后，以极小资金和硬限额运行；真实对账成交、拒单、撤单、费用、滑点、延迟和结算，任何不一致均停止。
5. **Live**：只有微实盘在预定样本和风险约束下通过，且监控、资本限额、归因、回滚、审计与合规均就绪后，才能另行批准扩容。

任一级失败都回到对应条目修订或关闭，不自动越级。

## 权限边界

**Registry 是研究与运营目录，不是交易、部署、AWS 写入、凭据使用、资本分配或实盘扩容授权。** `EXECUTABLE_STRATEGY` 只说明实验定义完整，不代表已验证盈利，更不代表允许下单。任何 shadow 之外的执行都必须经过现有权限、风险和显式授权流程。
