# 验收标准:引擎启动时的仓位接管(STARTUP TAKEOVER)

> Audit(Cowork Claude)· 2026-07-27 · **写在实现落地之前**
> 触发:07-27 切配对模式时,引擎带着 1 张 YES@67¢ 重启 → 预算护栏正确跳闸 → 操作员选择建接管能力(而非清仓绕过)。
> **本文的中心命题:接管能力天生就是安全网的洗白工具。今天跳闸的那道闸是对的,建这个能力最大的风险是把它废掉。**

---

## 0 · 一句话原则

**开机接管既有仓位 = 合法;运行中吸收对账差异 = 禁止。**
两者共用一份代码是本次最可能出的事故,必须在实现上物理隔离。

---

## G1 · 只在开机、只跑一次、只在报价之前

- 接管只允许在**进程启动、任何报价/下单之前**执行一次;
- 执行完置 `takeover_done=true`,**此后该代码路径在本进程生命周期内永不可再被调用**(不是靠约定,靠断言:再次调用 = 抛异常 + HALT);
- **运行中的 5 秒对账维持 fail-closed 原状:发现分歧 = HALT,永不采纳交易所状态。** 若本次改动让运行时对账变成"自动修正",本项直接不通过。

## G2 · 仓位可接管,挂单不可接管

- **仓位是事实**(交易所记着我持有几张,这个数唯一);→ 接管;
- **挂单是意图**(它背后有本地预留、配对腿归属、报价理由,重启后全部丢失);→ **开机时一律撤单,不许认领。**
- 撤单必须**确认成功**(轮询到活动挂单数=0)才允许继续;撤不干净 = HALT。

## G3 · 成本基准只能重建,不能推测

- 成本基准来源:**该市场的真实成交记录(fills)**,按时间重放,处理部分成交、多笔成交、反向抵消;
- 重放后的净张数**必须与交易所持仓完全相等**;不等 = **HALT,不许四舍五入、不许取最近一笔价、不许用中价代替**;
- 若 fills 拉取不完整(游标缺口、分页失败、时间窗不覆盖)= **HALT**;
- **禁止任何形式的"估算成本基准"。** 宁可拒绝启动。

## G4 · fail-closed 是默认分支

实现里每一个 `except` / `if not ok` 的默认动作必须是**拒绝启动**,不是"带着未知状态继续"。
审计方式:通读接管函数,**找出所有出口,确认非 HALT 出口只有一条**(全部校验通过)。

## G5 · 接管进来的仓位在熔断口径里必须显式

- 接管仓位的**历史浮亏不计入本 session 的 −$10 熔断**(沿用 F4 session-scoped 原则),
- 但**它接管之后产生的盈亏全额计入**;
- **两者必须分别落账、分别显示在 dashboard**,不许合并成一个数。理由:合并会让"继承来的亏损"隐形,下一次就会有人拿它解释当天的红字。

## G6 · 接管后第一件事是把它当孤腿处理,不是当库存忽略

- 接管的仓位必须立刻进入持仓重估回路(有出场判据),
- **不允许出现"接管成功但没有任何部件负责它"的状态**——那正是 07-27 那张 YES@67¢ 三次判 sell_rich 却无人执行的同一个形状。

## G7 · known-answer,先红后绿

上实盘前必须有失败记录再有通过记录:

1. 交易所有仓位、本地无账本 → 接管成功,成本基准与手工核对一致;
2. fills 故意截断一笔 → **必须 HALT**(不得凑出一个数);
3. 交易所有活动挂单 → **必须撤净后才启动**;
4. 交易所仓位 = 0 → 接管为空操作,正常启动;
5. 接管完成后再次调用接管函数 → **必须抛异常**;
6. 运行中人为制造持仓分歧 → **必须 HALT,且不得被接管逻辑"修好"**。

**第 6 条是本次改动的核心回归测试:它证明新能力没有把旧护栏吃掉。**

## G8 · 存活断言(今天立的新规矩,本部件同样适用)

- 接管完成后写一条 `TAKEOVER_OK` 收据:接管张数 / 成本基准 / 用到的 fills 笔数 / 撤单数 / 耗时;
- **接管仓位非零,但 5 分钟内该仓位没有产生任何重估决策 = 报警**;
- 收据缺失 = 视为未接管,不许开闸。

---

## 交付

代码 commit + G7 六条 known-answer 的红/绿记录 + 一次干净的 `TAKEOVER_OK` 收据 + dashboard 上"继承仓位"与"本session盈亏"分列的截图。
**缺 G7 第 6 条 = 不予验收。**
