# 验收标准：作战主线图（ROADMAP_TO_LIVE / PLAN_TRADING_MASTER）

> 审计（Cowork Claude）写。**这是主线图的过关条件,建之前就照这个建,不是画完再挑。**
> 操作员指令:"把主线捋清,噪音全部刨除,但主线需经过审计,确保不影响现有 pipeline。"
> 下面 7 条,任一不满足 = 主线图不过关。

---

## 规则0 · 不许碰正在跑的东西(操作员点名的红线,最高优先)

**主线图是一份"规划文档",它不许触发任何对正在运行的采集/封存链路的改动。**

- 现场直播的 capture(watchtower)、封存链、S3 上传——**时间不可逆**。今天少采一天,这一天**永远补不回来**,而 20 天验证是全项目的日历瓶颈。
- **"刨除噪音"绝不许把 capture/seal 相关的任何东西标成噪音、降级、暂停、或"以后再说"。** 它们是承重墙,不是杂物。
- 主线图若认为某条采集该改 → **不许自己动**,在 BOARD 标 `WAIT_DECISION`,由操作员在 DECISIONS.md 拍板。
- **审计核法:** 主线图交付前后,capture 进程、封存链、上传任务的状态必须**完全不变**。有任何一项被这次"梳理"影响 = 直接否决。

## 规则1 · 收编 ≠ 删除

现有 5 份分图(MASTER_SEQUENCE / MM_ROADMAP / PLAN_MM_TEST_PROGRAM / DATA_COMPLETENESS_ROADMAP / PLANS_LEDGER)里的**每一道门,必须逐条**:
- (i) **映射进**新主线的某一关,或
- (ii) **显式列为"本次丢弃",并写明理由。**

**不许静默消失。** 合并文档时最容易发生的事故,就是把某份分图里唯一记着的承重门弄丢了。交付时附一张**映射表**(旧文档→旧门→新主线第几关 / 丢弃+理由),审计逐行核。

## 规则2 · 日期必须是依赖的函数,不许是拍出来的日历（本次最重要的诚实项）

现状:**L2 只有 3 个干净日**,而 B14 时间戳 bug 仍在污染 L2、W06 Stage-2 扩面被冻结。

那么——**"20 天验证 = 月底到位"这句话很可能是假的。** 如果干净 L2 要等 B14 修完才开始累积,**20 天的钟就不是从今天起算,是从 B14 落地那天起算。**

**主线图必须把验证日期写成依赖的函数,不是一个拍好的日期:**
> 验证就绪日 = B14 修复落地日 + 20 个干净封存日（W06 扩面影响覆盖面,另标）

并明确写出后果:**B14 今天修 vs 一周后修,挣钱日期就差一周。** 这是操作员要的"精准定位瓶颈"——含糊的月底 = 又一团浆糊。

## 规则3 · 并行必须画出来,不许把日历时间白等掉

瓶颈②(20 天)是**日历约束,催不动**。所以主线图必须显式画出:**在等这 20 天的同时,哪些活在并行跑**——尤其是瓶颈③(mm_backtest 不建模结算 PnL、tradingd 执行层未接线、Layer D 执行资格未做)和影子引擎。

**串行画法 = 白白空转一个月。** 主线图必须标清每一关是"串行(必须等)"还是"并行(等待期内做)"。

## 规则4 · 每一关必须有可证伪的过关条件

红黄绿灯**没有意义**,除非绿灯的定义是"**某个数字 ≥ 某条线**"。每一关必须带齐五项:

| 字段 | 要求 |
|---|---|
| 这一关是什么 | 一句人话 |
| 技术根因 | 具体到 bug/模块(如 B14 时间戳、Layer D) |
| 工程号 | 对应 W / WO 编号 |
| 卡在谁手里 | 哪条 agent 线 / 操作员 |
| **过关条件** | **可证伪:什么数字、什么口径、超过什么线才算绿** |

没有"过关条件"这一列的主线图 = 换了个漂亮排版的浆糊。

## 规则5 · C1 的缺口必须是一道关,不是脚注

C1(深度回补做市,57.2%/50.5%/52.0%,三天符号稳定)是目前最实的候选,**但它测的是"显示深度"回补,不是"我自己的单能不能成交"**——候选报告自己诚实标了这条,很好。

**主线图必须把"显示深度 → 真实成交(队列位置/被穿价才成交)"作为一道显式的关**,受 `agents/audit/ACCEPTANCE_影子做市引擎_成交真实性.md` 那 10 条门管辖。**不许把它写成脚注**——否则 C1 会拿着一个"不是它看起来那个意思"的数字被提拔上去。

## 规则6 · 单写者 + 老图标注,防止再变回浆糊

- 按 ROLES.md:主线图属 `docs/`,**只有策略 agent + 操作员能写**。
- 主线图建成后,5 份旧分图**顶部各加一行**:「本文档的门已收编进 ROADMAP_TO_LIVE 第 X 关,以主线为准」。
- **不加这行,三天后就会重新漂移成浆糊**——这是本次问题的结构性根因,必须一并治掉。

## 审计怎么核(交付后我逐条打勾)

1. capture / 封存链 / 上传状态**前后完全未变**（规则0,一票否决）
2. 旧门映射表**逐行齐全**,丢弃项都有理由（规则1）
3. 验证日期写成 **B14 的函数**,不是拍的日历（规则2）
4. 每一关标了**串行/并行**,等待期有活干（规则3）
5. 每一关五个字段齐全,**过关条件可证伪**（规则4）
6. C1 的"显示深度→真实成交"是**一道独立的关**（规则5）
7. 旧分图**都加了 superseded 行**,主线单写者（规则6）

## 一句话
**这张图的价值不在"看起来清楚",在"它逼着每一关给出一个能证伪的数字、并且老实说出日期取决于哪个 bug 什么时候修"。** 而它的第一条纪律是:**梳理规划的过程,一根手指都不许碰正在采数据的那条线。**
