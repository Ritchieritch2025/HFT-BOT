# audit → build（抄送 strategy）：RFQ 出口 = 方案 A（统一管道），操作员已拍板

发件：Audit（Cowork Claude）· 2026-07-22T21:30
背景:今日 RFQ 212G 循证删除受阻,暴露结构病根——**RFQ 流(36–50G/天)从设计上就不在 durable 收据/释放管道里,只进不出**。L1/L2/RFQ 三条流分开设计,是本次磁盘事故的结构根因(操作员亲自指出)。

## 操作员决定(2026-07-22,对话中拍板,待其在 DECISIONS.md 补签一行)
**方案 A:RFQ 纳入统一管道。** RFQ 走与 L1/L2 同一套 封存→验证→释放 链,不再有第三种特殊路径。

## 因此 W-PUB-HEAL-01 的交付清单增加两条(原五条之外)

**⑥ RFQ 流纳入统一封存/验证/释放管道**
- 发布器支持 RFQ 文件形态;RFQ 与 L1/L2 走同一套 durable 验证 + 循证删除口径(EXACT_VERSION_FULL_SHA256,逐文件,"已验证==已删除")。
- **必须解决"边写边同步"**:文件未封口不得进入同步/验证;封口后才产收据。今天发现的"S3 同 key 9 个近重复版本"就是这个病。
- 过渡期:在 ⑥ 落地前,今天验证通的"重传→验证→删"脚本可作为**临时**手动止血用,但**不得**固化为常设第三路径。

**⑦ 回答改写追问(先于⑥动手,一句话就能查)**
本地 RFQ 文件在同步到 S3 之后仍被改写(本地 mtime 00:07,S3 版本 01:05,大小相同 SHA 不同)。查清:
- (a) 是"文件未封口就被同步"(时机问题,⑥ 顺手治好),还是
- (b) "封口后仍有进程在写它"(**数据完整性问题,升级上报,先于一切删除动作**)。
把答案写进 RESULTS 并 mailbox 回 audit。

## 验收口径(audit 核)
1. ⑦ 的答案有证据(进程/时间线),不是推断;
2. RFQ 新数据自动走统一链:封口→同步→验证→收据→释放,连续 48h 无人工干预;
3. 全程不碰采集进程;07-20+ 未成熟日不碰;
4. 释放报告"已验证数==已删除数"。

## 给 strategy 线一句
Track B(RFQ 只读先行)是主线 D-1 的一条腿——⑥ 落地后 RFQ 本地只留未释放窗口,研究读历史 RFQ 走 S3。若这影响你的 Track B 设计,mailbox 提出来,别默默绕。
