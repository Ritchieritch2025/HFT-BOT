## 事故链(全部有 journal/stat 证据)

1. `tools/publication_generation.py` `_atomic_manifest_bytes()`(~L372)用 `tempfile.mkstemp` 写 `.publication-generations/{catalog.json,dim/date=*.json}`,**mkstemp 恒 0600 且代码从不 chmod** → 每个新世代清单文件天生 600。
2. witness/durable/daily 三个发布服务按组 `kalshi-publication` 读(UMask=0007 的 setgid 目录),读不了 600 → `LOCAL_GENERATION_INVALID: Permission denied`,witness 全 exit 2。
3. 07-17..20 之所以能过,是当时手工 chmod 过 660(mtime 佐证)。07-21 起没人再改 → **07-21/07-22 连续两晚错过 witness 窗口**。
4. 窗口错过后果:catalog 每晚翻代,07-21/22 的 dim 快照绑的旧世代(`5b78e69c` / `17ac5217`)本地 parquet 已被覆盖 → witness 现在报 `dim/catalog generation mismatch`,**producer 路径永久无法补发**。
5. 2026-07-23T19:0xZ 已手工把现存 4 个 600 文件(catalog.json + dim/date=2026-07-{21,22,23}.json)改 660,**改前后 sha256 与 mtime/inode 全等**(记录在会话日志;catalog=8b53428c…, dim21=045047b3…, dim22=74081fbc…, dim23=ae8d26b3…)。权限错误已消,只剩 mismatch。

## 追加取证(2026-07-23T21:10Z)· producer 自动路径从未独立工作过

mtime 铁证:所有历史 witness 成功都是**同一 catalog 小时内"重绑 dim 清单 + 立即 witness"的人工链**,不是稳态自动:

- dim-18 清单 mtime 07-20 22:53:46 → witness S3 LastModified 22:55:20(间隔 94 秒)
- dim-19 清单 mtime 07-20 22:54:05 → witness 22:56:38
- dim-20 清单 mtime **07-21 19:20:35**(事后重绑)→ 当小时内 witness
- dim-17 清单 mtime 07-18 17:54(同模式)

结构矛盾:witness 要求"日已封存"(T+1 中午)且 dim 绑定 == **当下** catalog 世代,但 catalog 世代**每小时 :08 翻代**(已实测定论:18:08→`f6765cb3`、19:08→`61150a60`、20:08→`27314f70`、21:08→`efdd58b4`,每班世代号都变且每班都以 600 落盘;21:08 班次为重启 3.5 小时后的稳态行为,排除暂态)。dim 绑定的相干窗口只有写后到下一个 :08 的几十分钟,永远覆盖不到 T+1 封存后的 witness 时刻 → **producer 自动路径设计性死锁,不只是权限事故**。

**今晚 07-23 的既成事实**:17:30 重启导致每日块提前于 17:48 跑掉,20:17 无 dim 重写;dim-23 绑定 `ae9e2dc4`,18:08 起已被翻代孤儿化。除非走重绑链,07-23 与 21/22 同命。
